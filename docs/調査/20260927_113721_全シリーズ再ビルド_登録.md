## 結論

1. **32品すべて build 成功**（exit 0・stderr 0 バイト）。うち `vcs.modified=false` ＝
   commit された source だけで build された物が 22品、`true`（各 repo の他人の未 commit 差分を反映）が 10品。
2. **pin 登録は core の 1 行だけ**が正当だった。core は clean HEAD（`6d3468e`＝`origin/main`）で
   再ビルドされ、配置中 binary は `6c4fcae` のまま。`components.core.version` を `6d3468e` へ進め、
   `deployment.go_binaries` 3件の `version` は配置成果物 pin として `6c4fcae` に据置いた
   （「component の version は source pin、各 binary の version はその成果物 pin」契約。
   `tools`・`workspace` と同じ形）。これで core の `check-workspace` drift が解消し、
   配置済み core 3品は `MATCH` のまま（実測）。
3. **他 component の pin は触っていない**。`llm`・`bench`・`switch_core` は HEAD が pin より進んでいるが
   worktree が dirty で「SHA で内容を保証できない」ため `sync-pins` の対象にできず、`make check-pins` は
   `status: blocked` のまま（他 thread の作業中差分であり、本登録で巻き込まない）。
4. **配備追随は Ren 承認待ち**（本番差替え・restart 不可の指示が続いているため）。

## 触っていない pin・未登録（Ren 判断待ち）

1. **本番配備**: 再ビルド 32品を `~/.local/bin` へ差し替えて `rencrow.service` 等 を restart するか。
   配備するなら core の `go_binaries` 3件の `version` を配備先 revision へ追随させる
   （「pin を更新したら配置も追随させる」の逆方向の整合）。
2. **DIRTY 10品**（`rencrow-llm`／`rencrow-llm-verify`／`rencrow-llm-node`・tools 5品・workspace 2品）:
   各 repo の未 commit 差分を反映しており SHA で内容を保証できないため、該当 repo の commit まで
   pin 登録できない（`scripts/sync_workspace_pins.py` が dirty を拒否する仕様）。
3. **assistant 2品**: `ecosystem.yaml` に `go_binaries` 定義が無い（`deployment.files` のみ）。
   配置物は `rencrow-assistant-verify`（`vcs.revision=d728f0f`・2026-08-27 配置）で component pin
   `fd1d085` より古く、`rencrow-assistant` は未配置。定義を追加するなら配置する成果物を先に確定させる。
4. **bench**: Go/Rust 成果物なし（Python harness）。追跡 `.py` 125件を `compileall` で構文検証し exit 0。
5. **switch_core**: `ecosystem.yaml` に binary 定義なし（source pin のみ）。Rust/bazel 製で、
   別 thread が 2026-09-27 00:58〜01:17 にビルド・配備済み（`~/.local/bin/rencrow-compaction`、
   `candidate.json` の `binary_sha256=3f6d6d61…`）。同じ `target/fork-build` を共有するため
   並列衝突を避け再ビルドしていない。
