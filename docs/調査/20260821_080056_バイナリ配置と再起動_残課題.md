## B. 検出toolの限界（設計判断が要る）

### B-1. 滞留確認がreadinessを保証しない

`start_and_settle`が確認できるのはprocessの生存だけで、serviceが応答可能かは見ていない。
**COREはlistenまで実測約145秒**かかるため、既定の8秒はCOREについて何も言っていない。

現状は`--dwell`で秒数を延ばせるだけである。恒久対処するなら、component別に
health endpointを引いてreadinessを判定する必要があるが、endpointの持ち方が
moduleごとに異なる（`/health/live`、`/health/ready`、`/api/tts/health`、
`/healthz`は存在しない等）ため、manifestかmodule側に契約を足す設計判断が要る。

### B-2. `DIRTY` と `UNSTAMPED` が exit code 0 を返す

driftを検出していないため0だが、**「SHAで検証できない」状態が正常終了として扱われる。**
監視へ組み込むと見落とす。

非ゼロへ変えるのが妥当だと考えるが、exit codeの意味を変える挙動変更のため保留している。
当面は`--json`のstatusを直接判定する。

### B-3. Go以外のbinaryにversion管理が無い

`UNMAPPED`として素通りしているもの。

```
rencrow_log_rotate.sh          RenCrow_CORE/scripts/
rencrow_system_monitor.sh      RenCrow_Tools/tools/system_monitor/
rencrow-storage-backup         shell script
llama-server (rencrow-embed)   外部backend
observer以外のgames資産、docker (gitea)
```

Goのbuild stampに相当する仕組みが無いため、同じ検出方式を適用できない。
scriptについてはcontent hashをmanifestへ持たせる案があるが未設計。

### B-4. 実行がoperator起点のみ

pinと配置のズレは、誰かがcommandを実行した時にしか判明しない。
今回`rencrow-eiga-catalog-gateway`が**23 commits前**まで放置されていたのは、
気付く手段が無かったためである。

[Binary redeployment](../binary-redeployment.md)の責務境界により、
このtoolをtimerで自動実行しないと決めている。通知だけを分離する設計が要る。

### B-5. 配置結果のreceiptが残らない

実行結果は標準出力にのみ出る。いつ何を何から何へ替えたかの証跡が残らない。
退避したbinary（`~/.rencrow/backups/<name>.replaced-<sha>`）だけが痕跡である。

### B-6. Linux user systemd以外のhost adapterが無い

Windows service、launchdは未対応。[Binary placement](../binary-placement.md)は
三OSで同じ論理契約を実行すると定めているが、この検出・再配置は未追随。

## C. unit契約のズレ（binary検出の対象外）

binaryのpin整合とは別に、**配布されているunitテンプレートと稼働中unitの一致は
誰も検証していない。** 実測で2件の実ズレと1件の未導入がある。

（`@RENCROW_REPO_DIR@`のようなplaceholder置換差分は正常であり、下記から除外している）

### C-1. `rencrow-image` の保存先が未移行

| | 値 |
| --- | --- |
| repo契約 | `/srv/rencrow/db/image/objects`、`RequiresMountsFor=/srv/rencrow/db`、mount無しならfail closed |
| 稼働中 | `~/.local/share/rencrow-image/outputs`（PNG 4枚） |
| 契約先の現物 | 空 |

`b12f45f production画像保存先のsystemd契約を統一`が配布物にだけ入り、hostへ未適用。
binary側はコード差分ゼロのため今の稼働に支障は無いが、契約とは食い違っている。

**データ移動、`.env`への`RENCROW_IMAGE_OUTPUT_DIR`追加、unit差し替え、
`image.json`の`output_dir`との優先順位確認**が要る。

### C-2. `rencrow-lyrics-collector` に排他制御が無い

```
repo   ExecStart=/usr/bin/flock -n %h/.rencrow/config/lyrics-collector.lock %h/.local/bin/rencrow-lyrics-catalog collect ...
稼働   ExecStart=%h/.local/bin/rencrow-lyrics-catalog collect ...
```

稼働側に`flock -n`が無い。timerは5分間隔で、1回の収集が5分を超えると
**多重起動する**。repo側はそれを防ぐ意図で入っている。

### C-3. `rencrow-watchdog` が未導入

RenCrow_COREが`rencrow-watchdog.service`/`.timer`（Viewer Tailscale Serve watchdog、
`ops_watchdog.sh once`）を配布しているが、hostに導入されていない。

導入すべきか、廃止済みなのかの判断が要る。

### C-4. drop-inがrepo管理されていない

CORE `rencrow.service.d` の内訳。

| drop-in | repo | host |
| --- | --- | --- |
| `10-panic-stack.conf` | あり | あり |
| `20-resilience.conf` | あり | あり |
| `30-games-observer.conf` | あり | **なし** |
| `40-codex-path.conf` | **なし** | あり |
| `50-movie-catalog.conf` | **なし** | あり |
| `60-person-related-catalog.conf` | **なし** | あり |
| `70-trade.conf` | **なし** | あり |

さらに、今回12サービスへ追加した無限リトライの歯止め`90-start-limit.conf`
（`StartLimitIntervalSec=300` / `StartLimitBurst=5`）は**どのrepoにも入っていない。**
hostを作り直すと歯止めごと消える。

所有moduleのrepoへ入れるべきだが、host固有値（`50-movie-catalog.conf`の
`RENCROW_MOVIE_CATALOG_CRAWLER_URL`等）を含むものがあり、どこまでを配布物に
するかの線引きが要る。

## D. 未解明

### D-1. resilience watchdogが6日間トリガーゼロ

```
timer  ActiveState=active / UnitFileState=enabled
       LastTriggerUSec         = 2026-08-15 00:06:13 UTC
       NextElapseUSecMonotonic = infinity
boot                           = 2026-08-15 04:24:21 UTC
```

**最後の発火は現在のbootより前**で、以降トリガーゼロ、次回予定も無い。
timerは`active`と表示されるため、状態一覧では正常に見える。

unit定義は妥当で、**repo版と稼働版は完全に一致している**（unit driftではない）。

```ini
OnBootSec=30s
OnUnitActiveSec=30s
AccuracySec=5s
Persistent=true
Unit=rencrow-resilience.service
```

`OnBootSec=30s`がある以上boot+30秒で発火すべきで、`NextElapse=infinity`になる理由は
未特定。`Persistent=true`は`OnCalendar`専用のため、ここでは効かない。

**影響**: COREの事故検知と自己修復（`RENCROW_RESILIENCE_AUTO_REPAIR=true`、
CODE2経路）が6日間停止している。systemdの`Restart=always`があるため落ちても
上がり直すが、事故台帳への記録と自己修復は働いていない。

推測で直さず、原因を特定してから対処する。

### D-2. CORE の `StartLimitIntervalSec=0` を維持するか

12サービスには5分窓5回の歯止めを入れたが、CORE だけは`20-resilience.conf`の
`StartLimitIntervalSec=0`（上限なし）を維持している。

```
# RenCrowは連続異常終了時にもsystemdのstart limitで停止しない。
```

resilienceの事故台帳（`ExecStopPost=rencrow resilience capture-stop`）と対の設計のため
弱めていない。ただし**D-1でそのresilienceが動いていない**ため、現状はCOREだけが
無限リトライしうる状態で放置されている。D-1の解決とセットで判断する。
