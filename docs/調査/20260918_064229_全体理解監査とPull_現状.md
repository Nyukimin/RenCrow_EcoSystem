## Failure Knowledge（① boot mount 競合と③ llm readiness の追記）

- **Failure**: mount 依存を宣言している user unit が boot 時に `mountpoint` 失敗で exit 32 と start-limit に達し、`failed` 固定になる。
- **Problem**: `RequiresMountsFor=` を書いてあっても `ExecStartPre` 側の mount 判定が先に走り、trade/observer の正規 route が boot 以降ずっと死んでいる（health なしでは表面化しない）。
- **Cause**: `srv-rencrow-db.mount` の ActiveEnter（06:30:43）より user unit の起動（06:30:33）が 10 秒速い。`RequiresMountsFor` は `Wants`+`After` を付けるが、`nofail` / `LABEL=` 解決の遅延と user manager の起動順により ordering が実効化されていない。
- **Lesson**: mount 依存は宣言ではなく**待ち合わせの実装**で保証する（`ExecStartPre` 前の猶予、`systemd-mount --wait`、または mount unit 側の `Before=` 明示）。
- **Invariant**: 共有ストレージを読む unit は、mount 完了を待たずに失敗固定してはならない。失敗時は start-limit を超えない再試行と、`failed` の観測可能条件を持つ。
- **Enforcement**: unit 正本文の `ExecStartPre` 要求行を各 owner の契約 test が**完全一致行として固定**（TRADE `scripts/tests/durable_store_contract.py` / Image・GAMES `systemd/user/service_contract_test.go`、`9bced0b` 等で更新済）。unit と配置 unit の二重定義を防げているのはこの固定行による。
- **Tests**: boot 競合そのものを再現する test は**未整備**（猶予付き `ExecStartPre` の等效 probe は手動実施、実 boot 再現は未実施）。復帰手順は `systemctl --user reset-failed <unit> && systemctl --user start <unit>`（drop-in `90-start-limit.conf` のコメントに記載済）。

- **Failure**: readiness 契約の期待値が配置 binary の実 payload と食い違い、unit が `active` で route が 200 でも監査が fail する。
- **Problem**: `--check-readiness` の llm 項目が 180s timeout で fail し、route 実測（200・targets 9 件 ready）と矛盾する。見かけ上は route 障害、実体は manifest のピン留めが古い。
- **Cause**: `components.llm.version` が `079c79c`（09-01）に固定的に残る一方、配置 binary は HEAD `ad6287f`（09-17、30 commits 先行）。pin の時点では `{"status":"ok"}` が正しかったが、pin の子孫である `1ec2902`（09-12）で `/health` が live alias（`status=live`）へ変わった。**期待値の誤記ではなく pin drift**。
- **Lesson**: readiness 契約は `expect`（期待 payload）と `component.version`（その期待値が正しい commit）を**対として同じ変更単位で更新**する。配置を進めて pin を据え置くと、契约 test を通しても監査が構造的に fail する。期待値を単独で書き換えるのは drift を隠す第 2 の定義の追加であり禁止。
- **Invariant**: readiness 契約の期待値は、manifest が pin した version の health 契約正本から決定的に導出されなければならない（配置実体にも、module 実装の手書き値にも追随させない）。
- **Enforcement**: **部分整備（2026-09-18）**：期待値の単独ドリフトは既存契約 test `tests/test_validate_ecosystem.py::test_production_user_systemd_readiness_contracts_are_declared` が期待 tuple を固定しており、pin だけ上げて `expect` を放置／`expect` だけ変えると test が fail する（今回の対更新で確認）。一方 `validate_ecosystem.py` は readiness の**形**（url loopback / `expect={path,equals}` / equals が JSON scalar）のみ検証し、payload 値を module 仕様正本や pin version から導出する仕組みは**未整備**。
- **Tests**: 上記契約 test は期待値を pin 側へ固定する（今回 `ok`→`live` の対更新で有効性を実測）。ただし**新 pin の health 契約正本（module の `docs/06_Public_API仕様.md`）から期待値を自動導出する突合 test は未整備**のため、次回 health 契約変更でも同じ pin drift が再発しうる。
