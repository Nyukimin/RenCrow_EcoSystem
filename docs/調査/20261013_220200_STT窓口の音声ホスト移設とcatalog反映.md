# STT窓口の音声ホスト移設とcatalog反映（2026-10-13）

## 概要

STT窓口（`rencrow-stt`）がCOREホストのuser systemdからmacOS音声hostのsystem LaunchDaemonへ
移った。catalogの`components.stt`は「COREホストでuser unitが稼働する」前提のdeployment契約を
持つため、移設後の扱い（source pin、artifact pin、drift検査、再配置、readiness検査）を
読み取りだけで確認し、反映方法を決めた。あわせて音声engineのrepository
`RenCrow_Whisper`（owner `stt`）と`RenCrow_Irodori_TTS`（owner `tts`）を
`runtime_profiles`へ登録した。ホスト番号・IP・user名・実pathは公開repoのため記載しない。

## 発生条件

- STT窓口がmacOS音声hostのLaunchDaemonで稼働し、COREホストの`rencrow-stt.service`は
  stop／disableされた。COREホストのloopback port（窓口の公開port）は転送unitが保持する。
- catalogの`components.stt`は`deployment.user_systemd`に`rencrow-stt.service`
  （readiness `/health/ready`）を宣言している。

## 手順

1. COREホストへ読み取りだけのSSH（`is-enabled`／`is-active`／`list-unit-files`／`cat`）を実行した。
2. COREホストのcatalog checkoutでcheckerを`--json`と`--check-readiness`で実行した
   （どちらも状態を変えない。`--apply`は実行していない）。
3. `scripts/check_deployed_binaries.py`と`scripts/deployment_host_adapters.py`を読み、
   停止中unitの扱いと、unitをenable／startする処理の有無を確認した。
4. `RenCrow_Tools`のstart-limit installerと`RenCrow_Workspace`／`RenCrow_CMD`を検索し、
   `rencrow-stt.service`をenable／startする処理の有無を確認した。

## 事実

- COREホスト: `rencrow-stt.service`はdisabled／inactive、転送unitはenabled／active。
  毎時のdrift通知timerは稼働中で、通知対象は`MISMATCH`／`DIRTY`／`UNSTAMPED`の集合変化のみ。
- drift: COREホストの`rencrow-stt`は`26069cb`でbuildされ、`go_binaries[].version`
  （artifact pin）と一致して`MATCH`。managed file `stt.json`のhashも一致。
- `RenCrow_STT`の`main`は`c451b6d`で、`26069cb`から3 commit進んでいる
  （whisper.cpp用target protocol、macOS LaunchDaemon一式、手順文書）。
  `config/checks/runtime.json`のSHA-256は両revisionで同一。
- `collect()`は`list-unit-files`で停止中・disabledのunitも列挙する（binaryが実在するunitのみ）。`redeploy()`は
  `_running_units`で稼働中のunitだけを再起動対象とし、停止中のunitは停止のまま据え置く。
  `systemctl enable`を呼ぶ処理はdrift通知timerのinstallerだけである。
  `RenCrow_Tools`のstart-limit installerはdrop-inとdaemon-reloadだけで、enable／startしない。
  `RenCrow_Workspace`と`RenCrow_CMD`に`rencrow-stt.service`への参照は無い。
  よって`rencrow-stt.service`をdisabledに保つ限り、自動で再有効化する処理は無い。
- `launchd` host adapterはuser領域のLaunchAgent（`gui/<uid>`）だけを扱い、system
  LaunchDaemonは対象外。manifestの`deployment`が許可するkeyは`user_systemd`／`files`／
  `go_binaries`だけで、LaunchDaemonを表す形式は無い。
- `--check-readiness`（COREホストで実測）: `http_json`契約のunitは稼働状態に関わらず
  `wait_for_readiness`へ渡され、`rencrow-stt.service -> inactive/dead`でexit 1になる。
  以降のunitの確認へ進まない。unitの稼働を前提とする検査が、窓口の移設後は停止中のunitに当たりNGになる。

## 結論

- 採用: `components.stt.version`（source pin）だけを`c451b6d`へ進める
  （`make sync-pins`）。`go_binaries[].version`（artifact pin `26069cb`）、`files`のhash、
  `user_systemd`は変えない。2026-09-27の再ビルド登録と同じ「source pinを進め、artifact pinを
  据え置く」形で、COREホストのdriftは`MATCH`のまま、通知の集合も変わらない。
  source pinを進めないと、`c451b6d`のcheckoutで`check-workspace`が落ちる。
- 不採用: LaunchDaemonをmanifestのdeployment形式として追加する案。検査主体（adapter）が
  無いまま宣言だけが先行し、検査されない正本になる。必要になった時点で、adapterとvalidatorと
  同じ変更で扱う。
- 不採用: `--check-readiness`の停止unitの扱いを変えるchecker変更。既存toolの挙動変更であり、
  今回の依頼範囲外。選択肢は(i) `http_json`契約のunitも稼働中のものだけを対象にする
  （他の契約と対称にする）、(ii) 現状維持で既知の限界として文書化する。今回は(ii)を実施し、
  `docs/binary-redeployment.md`の既知の限界へ記載した。
- 文書: 配置の扱いは`docs/binary-redeployment.md`（既知の限界）と
  `docs/runtime-layers.md`（STT節）へ記載した。

## Failure Knowledge

- Failure: 窓口をCOREホストの外へ移した結果、`--check-readiness`が常時exit 1になった。
- Cause: `http_json`契約のunitが「必ず稼働している」前提で検査される。
- Lesson: 窓口の配置を変えるときは、deployment契約とreadiness検査の前提を同じ変更で見直す。
- Invariant: 未確認・未強制。現状は文書化のみ（強制する検査は無い）。
- Enforcement: 未実装（上記(i)の変更とtestが候補）。
- Tests: 無し。
- 後続: 2026-10-14に`remote_gateway`契約で解消した。
  [20261014_072650](20261014_072650_STT窓口のremote_gateway契約化とreadiness検査.md)を参照。
