## 1. 結論

Codexの技術的上限は高く、複数repo・API変換・runtime配布・実I/Oまで成功させた事例があります。  
一方、通常時の再現性は上限より明確に低く、最大の弱点は「実装能力」ではなく「何をもって完了とするか」の粗さです。  
特に、catalog登録・unit test・health・局所E2Eを、ユーザーが要求した実利用経路の完了と誤認するパターンが残っています。  
訂正後の回復力は高いものの、ユーザーが何度か追及して初めて前提を更新する例もあります。  
総合評価は、Coding 6.7、Specification 7.6、Debugging 7.0です。仕様作成が最も安定し、Completion integrityが3能力共通のボトルネックです。

### 繰り返し評価されている強み

- 概念を正確に整理できたとき、ユーザーは「仕様にして」「それを正本へ」と次工程を任せています。
- repo・正本・live copy・runtime経路を分け、実際のI/Oまで証明した作業は、その後の訂正が少ない傾向です。
- 訂正後に前提を更新し、wrong repoの変更を戻して本体へ移す、仮説を棄却する、実Agent経路まで作り直す回復力があります。
- dirty worktreeを保持し、対象差分だけcommit・pushする運用は7～8月に安定しています。

### 繰り返し訂正されている弱点

- 実機表示を頼まれたのにunit test・局所ログ中心で「直った」と判断する。
- owner repoやcanonical sourceを確定する前に編集する。
- 「catalogに載っている」「ToolIDがある」「restricted理由がある」を、実行可能な経路と混同する。
- ユーザーの既知正常時点や過去sessionを読まず、説明しやすい仮説へ早く固定する。
- 一般論を、repo固有の回答として返す。
- health、focused test、backend直結成功を、client／proxy／Agent route全体の成功と混同する。

### 満足・不満から分かる成功条件

成功条件は「コードがある」ではなく、次の連鎖です。

`正しいowner → 正本 → build成果物 → live設定 → listener/readiness → ユーザーが要求したroute → 観測可能な結果`

失敗条件は、このどこかを省略して「完了」「100%」と報告することです。

### 強み

### 弱み

- 実装着手前のowner確認がgateになっておらず、RenCrow_CMDへ先に編集した例があります。

### 成功事例

- Responses API修復では、backend生成、Responses変換、SSEイベント順、stale `Content-Length`、model alias、Codex CLI表示を別境界として確認しました。
- Tool／Skill／MCP原則の実装では、Workspace正本、CORE strict loader、tests、push、live同期、binary一致、readiness、Mio実チャットまで確認しました。
- To-Be仕様のpushでは、既存未コミット差分を混ぜず、docs差分だけをcommitし、後続の全pushでも対象を分けています。

### 失敗事例

- 全DB対応では、最初に「20/20・実Agent E2E・完了」と報告しましたが、ユーザーの追及後、通常会話のpublic scopeから内部owner routeへ接続できないと認めています。これは明確なfalse completionです。
- その後20-store契約を回復しましたが、Bookmark／Newsを追加確認すると、保存・取得はできても通常想起やpromotionが未完成でした。「20 catalog entries」と「全データsourceの利用可能性」が再びずれています。
- IdleChat Viewerでは、tests・build・restart後もユーザーの実機観測で表示が改善しておらず、目視確認の内容そのものを強く批判されました。

### 根本原因

- implementation stateを`存在する／しない`程度で管理し、`source変更済み／build済み／deployed／requested route実証済み`を別stateにしていない。
- 作業開始時より、実装中にowner・正本を確定することがある。
- final answerが工程別evidence matrixから生成されず、直近の成功結果に引っ張られる。
- Ruleは正しいものの、違反しても実行を停止する機械的gateがありません。

## 10. 修正優先順位

### P0

1. Completion Evidence Gateを必須化する。
2. 編集前にowner repo、canonical source、live artifact、requested routeを固定する。
3. ユーザー訂正を、そのturn以降の強制制約へ昇格する。
4. 同じ仮説／同じtool失敗が2回続いたらstrategy resetする。

### P1

1. 仕様へCurrent／Target／Unimplemented／Deployedを機能単位で表示する。
2. debugging hypothesis ledgerを使う。
3. final answerをrequested verb matrixから生成する。
4. subagent成果はmain agentのdiff・test再確認が終わるまでadvisory扱いにする。

### P2

1. 月次でsession outcomeを再監査する。
2. summary coverageとstale summaryを検出する。
3. Tool実行契約の短いself-testをSkillへ持たせる。
4. 長大sessionで目的が変わったら新しいcompletion matrixを作り直す。

## 12. 未確認・限界

- 364 rolloutすべてを人間同等の深さで読んだわけではありません。全件構造集計後、複数月・複数能力から代表sessionを深掘りしました。
- summary 70件は自己要約biasを含みます。実際、全DBsummaryは初期partialを正しく記録する一方、同じ巨大sessionの後続回復を表していません。
- thread DBは8月中心で、全期間のcommand／file-change母数ではありません。
- raw sessionはcompactionやforkで同じ内容を再掲するため、単純keyword・tool-call件数は独立試行数ではありません。
- OS portability、concurrency、subagent diff reviewは、他の軸より一次証拠が少なく、採点confidenceが低めです。
- 現在のrepo・runtime状態は再検証していません。これは過去作業品質監査であり、現行稼働監査ではありません。
- system、network、hardwareの実障害とAgent判断ミスを分離しました。例えばUSB障害やproxyのTool-call欠落そのものはAgentの能力不足ではなく、その扱い方を評価しています。
- 今回は監査時点でファイル、DB、Memory、設定、runtimeを変更していません。本書の保存のみが、その後に明示された変更です。
